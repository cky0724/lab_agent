# Claude Code 记忆系统：六层模型

> **本文是基于 Claude Code 源码逆向分析的技术调研文档，用于面试时展示对 Agent 记忆机制的深度理解。**

---

## 核心框架：六层记忆模型

这是我从源码逆向分析得出的框架（官方文档未明确划分），按**作用域**、**生命周期**和**执行顺序**组织：

| 层级 | 名称 | 作用域 | 生命周期 | 核心功能 |
|------|------|--------|----------|----------|
| ① | 指令记忆 | 规则级 | 永久 | 加载 CLAUDE.md 开发规则，定义项目约束 |
| ② | 短期记忆 | 会话级 | 会话结束销毁 | messages[] 数组，承载对话历史 |
| ③ | 工作记忆 | 任务级 | 会话结束销毁 | 工具状态、进度、重试计数 |
| ④ | 长期记忆 | 持久级 | 永久 | Auto Memory 自动提取，跨会话复用 |
| ⑤ | 压缩记忆 | 压缩级 | 会话内有效 | 上下文达水位时生成摘要，防止溢出 |
| ⑥ | 休眠重塑 | 离线级 | 跨会话后台 | 整理长期记忆，合并重复项 |

**一句话总结**：指令记忆定规则，短期记忆管当下，长期记忆沉经验，压缩防溢出，休眠做保养。

## 阶段一：会话启动加载

系统按固定顺序扫描并合并所有 CLAUDE.md 文件，随后加载长期记忆索引，最终组装 System Prompt。

### 加载顺序（优先级从高到低）

| 次序 | 作用域 | 说明 |
|------|--------|------|
| 1 | 组织托管 | 企业下发的全局指令（用户不可改） |
| 2 | 用户全局 | `~/.claude/CLAUDE.md`（跨项目生效） |
| 3 | 项目级 | 项目根目录的 CLAUDE.md（随 Git 提交） |
| 4 | 项目本地 | `CLAUDE.local.md`（不提交，个人定制） |
| 5 | 记忆索引 | `memory/MEMORY.md`（自动记忆） |
| 6 | 置顶记忆 | 标记为 pinned 的记忆（最多 4 条） |

**关键设计**：
- 冲突时遵守**就近原则**（项目级 > 用户全局）
- 单文件有 4MB 上限，超限直接跳过
- 置顶记忆永远在场（不依赖召回），用于存放"每次都必须知道"的规则

## 阶段二：每轮对话执行循环

每轮循环的核心流程：

```
1. 用户输入 → 追加到 messages[]（短期记忆）
2. 记忆召回（从 memory/ 中检索相关记忆）
3. 微压缩（按需清理旧工具输出）
4. 组装上下文：System Prompt + messages[] + 召回记忆
5. 调用主模型 → 执行工具调用
6. 工具结果追加 messages[] 并落盘
7. 更新工作记忆（进度/状态）
8. 返回结果，等待下一轮
```

### 记忆召回（每轮触发）

**这是模型"想起"具体记忆的唯一方式**，不是启动时做一次，而是**每一轮用户输入都会执行**：

```
用户输入 → 索引检索 → 过滤已展示 → 按相关度排序 → 取前 5 条 → 语义选择 → 注入当前回合
```

**关键设计**：
- 召回 5 条，置顶 4 条（置顶不依赖召回，永远在场）
- 有相关度地板（relevance floor），分数不够宁可不召回
- 选择器用独立的小模型（Sonnet 档位），不占用主模型上下文

### 微压缩 vs 全量压缩

两种压缩策略配合使用，防止上下文溢出：

| 维度 | 微压缩 | 全量压缩 |
|------|--------|----------|
| 触发时机 | 每轮都执行 | Token 达水位线时触发 |
| 压缩对象 | 旧工具输出 | 整段对话历史 |
| 是否调模型 | 否（规则清理） | 是（生成摘要） |
| 信息损失 | 低（只丢旧输出） | 高（历史被替换） |
| 成本 | 零 | 额外消耗 token |

**微压缩**：预估可省 ≥20000 token 才参与，保留最近几条工具结果，更早的替换为占位符。
**全量压缩**：到水位时 fork 子 Agent 生成对话摘要，把整段历史换成摘要。

## 阶段三：上下文管理与压缩

**核心思想**：上下文达水位时，fork 子 Agent 生成对话摘要，把整段历史换成摘要。

**压缩摘要的 9 个 Section**（固定模板）：
1. 用户请求与意图
2. 关键技术概念
3. 涉及的文件与代码
4. 错误与修复
5. 问题求解进展
6. 全部用户消息（逐字保留）
7. 待完成任务
8. 当前工作（含文件名/代码片段）
9. 下一步动作（引用用户原话）

**设计要点**：保留原话、保留错误、保留没做完的、下一步引用用户原话——这四条是摘要质量的保证。

## 阶段四：长期记忆写入

**这是唯一跨会话持久化的动态记忆层**，存储在 `~/.claude/projects/<project>/memory/` 目录。

**四种记忆类型**：
- user（用户身份/偏好）
- feedback（用户反馈，正负都要记）
- project（项目事实/决策）
- reference（外部系统指针）

**筛选标准**：只记"跨会话还有价值、且从代码推不出来"的信息。代码模式、架构分析这类能自证的东西明确不记。

**关键设计**：
- **记忆是提示，不是真理**：注入时会警告"引用前必须先验证它现在还存在"
- **正负反馈都要记**：只记批评会导致模型过度谨慎、事事请示
- **权限沙箱**：Fork 子 Agent 仅能读写 memory 目录，禁止访问源码/Bash/联网

## 会话生命周期总结

| 对象 | 所属层 | 会话结束时的处理 |
|------|--------|------------------|
| messages[] 数组 | ② 短期记忆 | 销毁 |
| 工作记忆 | ③ 工作记忆 | 清空 |
| 压缩摘要 | ⑤ 压缩记忆 | 会话内有效 |
| memory/*.md | ④ 长期记忆 | **保留，永久** |
| CLAUDE.md | ① 指令记忆 | **保留，永久** |

## 附录：关键设计洞察

### 数据流向

- **跑模型** → 发给配置文件里配的模型（接第三方就是第三方）
- **取开关/上报** → 发给 Anthropic 官方服务（地址写死，无法改）

**核心结论**：
1. 没有"记忆服务器"，六层全是本地内存和本地文件
2. 断网也能用（只有模型调用离不开网）
3. 第三方环境下 AutoDream 无法使用（开关从官方获取）

### Fork 子 Agent 的设计哲学

**Fork ≠ 生成**。Fork 来自 Git，意思是"另起一条线程、跑完不污染主线"。

**它做了什么**：子 Agent 启动时，把主会话的 messages 作为初始上下文塞进去，干完只把结果交回来，中间过程不进主线对话。

**为什么必须 Fork**：提取记忆、写压缩摘要这类活儿，如果直接在主线里跑，模型会在 messages[] 里看到"自己跟自己开会"，把对话流搞乱。Fork 让后台活儿另起一条线——**主线干净，结果回流**。

## 与本项目的对照：为什么选方案 1

### 三种记忆方案对比

| 方案 | 实现方式 | 本项目选择 | 原因 |
|------|---------|-----------|------|
| 消息列表拼接 | 内存中维护 messages[] | ✅ **采用** | 实现简单，业务链路稳定，无跨会话持久化诉求 |
| Checkpointer | LangGraph 原生状态持久化 | ❌ 未采用 | 需额外存储组件，当前业务场景无需中断恢复 |
| Claude Code 文件式记忆 | 分层记忆 + 自动提取 | ❌ 未采用（调研方向） | 工程复杂度高，需额外实现提取子 Agent |

### 选型理由

**当前场景**：单轮对话为主，对话轮次短（平均 3-5 轮），无跨会话持久化诉求。

**方案 1 的优势**：
1. 实现简单，零额外依赖
2. 工具调用链路稳定，无状态丢失风险
3. 上下文窗口充裕（qwen-plus 支持 32K token），无需频繁压缩

**方案 1 的局限**：
1. 会话刷新后记忆丢失
2. 对话轮次过多时上下文膨胀
3. 无法复用历史经验

### 后续迭代方向

**短期优化**（低成本）：
- 增加上下文预算管理（token 预估 + 截断策略）
- 实现对话摘要（会话结束时生成关键要点）

**中期规划**（Claude Code 方案借鉴）：
- 实现分层记忆：会话层（当前 messages[]）+ 项目层（memory/*.md）
- 增加记忆召回：每轮对话前检索相关记忆注入上下文
- 设计记忆筛选标准：只记"跨会话有价值、代码推不出来"的信息

**长期愿景**（生产级 Agent）：
- 实现 AutoDream 机制：后台异步整理长期记忆
- 增加记忆压缩：定期合并重复项，控制索引大小
- 设计记忆权限沙箱：防止记忆污染项目代码

### 面试话术总结

> "我们项目选择了最简单的消息拼接方案，因为当前业务场景是单轮对话为主，对话轮次短（平均 3-5 轮），没有跨会话持久化的需求。方案 1 的优势是实现简单、链路稳定、零额外依赖。但我也调研了 Claude Code 的六层记忆模型，认为它是生产级 Agent 的标杆设计——分层清晰、自动提取、断网可用。如果后续业务复杂度增加（比如长对话、多轮协作、跨会话经验复用），我会考虑引入分层记忆 + 自动提取机制，借鉴 Claude Code 的设计哲学。"

## 面试高频问题预案

### Q1: "为什么不直接用 LangGraph Checkpointer？"

> "Checkpointer 是为中断恢复设计的（比如 Human-in-the-loop 暂停等用户确认）。我们当前的场景是单轮对话，无需中断恢复，所以用 Checkpointer 属于过度设计。而且 Checkpointer 需要额外持久化存储（SQLite/Postgres），增加了系统复杂度。我们优先保证主链路稳定，后续如果有中断恢复需求再引入。"

### Q2: "你怎么知道 Claude Code 的记忆系统设计得好？"

> "我逆向分析了它的源码，发现几个关键设计：① 分层清晰（六层模型各司其职）；② 自动提取（不依赖用户手动维护）；③ 断网可用（全是本地文件）；④ 权限沙箱（记忆提取不能污染代码）。这些设计解决了记忆系统的核心矛盾：既要持久化经验，又不能污染项目代码。"

### Q3: "如果让你优化当前项目的记忆机制，你会怎么做？"

> "短期：增加上下文预算管理（token 预估 + 截断策略），防止对话过长时上下文溢出。
> 中期：借鉴 Claude Code 的分层记忆，实现会话层（当前 messages[]）+ 项目层（memory/*.md），每轮对话前检索相关记忆注入上下文。
> 长期：实现 AutoDream 机制，后台异步整理长期记忆，定期合并重复项，控制索引大小。"
