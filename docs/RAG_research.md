# RAG 技术调研
> 用于项目技术调研，区分标准RAG与高级RAG，梳理链路、选型权衡与固有局限，可直接放入项目文档。

## 总览
RAG（检索增强生成）核心思想：不依赖大模型训练时的固有知识，从私有业务文档中召回相关文本片段，拼接至提示词辅助模型生成回答。
用于解决私有知识库问答，缓解大模型幻觉，但无法完全消除幻觉。
分为**标准RAG**与**高级RAG**，需要根据文档复杂程度选择方案。

| 模块          | 作用                    | 生命周期       | 备注                   |
| ------------- | ----------------------- | -------------- | ---------------------- |
| 文档预处理    | 文档清洗、分块、向量化  | 持久化         | 离线构建阶段           |
| 向量库        | 存储向量与原始文本块    | 持久化         | 检索数据源             |
| 查询预处理    | Query重写、Query扩展    | 单次会话       | 可选，需要权衡调用成本 |
| 检索器        | 向量检索 / BM25混合检索 | 请求时实时执行 | 生产环境优先混合检索   |
| 重排序 rerank | 对召回结果二次打分过滤  | 单次会话       | 提升上下文质量         |
| 大模型生成    | 结合检索上下文输出答案  | 单次会话       | 最终输出               |

## 阶段0：离线知识库构建
> 离线执行，支持定时增量更新，不占用问答接口耗时

1. **文档清洗**：去除无效换行、乱码、页眉页脚等噪声内容。
2. **Chunk切分**
    - 简单文档：按标题 → 段落 → 句子 → 字符的优先级切分；设置`overlap`重叠窗口，避免完整语义被切断。
    - 复杂强关联文档：使用大模型做**语义切分**，按照语义边界分割，Token开销更高。
3. **Embedding向量化**：使用Embedding模型将文本块转化为向量表示。
4. **向量库入库**
    - 开发调试：Chroma，轻量无需额外部署。
    - 生产环境：Milvus，支持分布式，适配海量向量数据。

## 阶段1：在线问答执行链路
用户原始问题
→【可选】Query重写/扩展（大模型调用，权衡成本）
→ Query向量化
→ 检索：向量相似度检索 + BM25关键词检索，RRF分数融合
→ rerank重排序，筛选top5‑10高相关chunk
→ 检索上下文 + 用户问题组装Prompt送入大模型
→ 模型输出最终回答

### 链路关键要点
1. **Query重写（可选）**
对模糊问句做改写，生成多条变体Query提升召回效果；会增加LLM调用开销，小型项目可关闭。

2. **混合检索（生产推荐）**
- 纯向量检索：擅长语义匹配；缺点是专有名词、编号容易漏召回，会召回语义相近但事实无关的内容。
- BM25关键词检索：擅长精确关键词命中，不理解语义。
- 通过 **RRF倒数排名融合** 合并两套检索得分，兼顾语义理解与关键词精准命中。

3. **Rerank重排序**
对初筛得到的文本块做二次相关性打分，过滤低质量片段，减少送入大模型的冗余上下文；存在额外推理开销。

## 阶段2：高级RAG方案（调研，MVP未落地）
> 适用场景：文档实体多、文档之间存在大量关联关系，普通扁平Chunk会割裂实体关联。

### GraphRAG
由大模型从文档提取实体以及实体之间的关系，构建知识图谱；检索时顺着实体关系游走，拉取关联文本片段。
- 优点：适合处理实体繁多、事件链路复杂的文档。
- 缺点：图谱构建Token消耗大；实体提取容易出错；后期维护成本高。

### Agentic‑RAG
抛弃固定流水线，交由Agent自主决策：是否改写Query、是否需要多轮检索、切换检索策略。
- 优点：业务复杂问题下灵活性高。
- 缺点：多轮调用带来更高延迟与成本；Agent存在推理跑偏风险，需要增加结果校验。

## RAG固有局限
1. 召回缺陷：切分不合理、Embedding模型不匹配会造成相关文档召回不到位；混合检索+rerank只能缓解，不能根除。
2. 无法彻底消除幻觉：即使检索到正确文档，大模型仍可能篡改、脑补信息；可增加引用溯源，附带文档来源便于校验。
3. 高级RAG能力更强，但算力、复杂度同步上涨；业务简单场景优先使用标准混合检索RAG。

## 与本项目对照：当前实现与优化方向

### 当前项目实现

**知识库规模**：8 个实验室 + 4 个知识文档（开放时间/预约规则/安全规范/设备说明）

**技术选型**：
- 向量库：Chroma（轻量，无需额外部署）
- Embedding：bge-small-zh-v1.5（中文效果优，推理成本低）
- 检索策略：纯向量检索（top-k=2）
- Chunk 策略：全文档入库（文档短小，无需切分）

**代码示例**（核心检索逻辑）：
```python
# kb_service.py
def search_kb(query: str, top_k: int = 2):
    # 1. 向量化查询
    query_embedding = embed(query)
    
    # 2. 向量检索
    results = collection.query(
        query_embeddings=[query_embedding],
        n_results=top_k,
        include=["documents", "metadatas", "distances"]
    )
    
    # 3. 组装上下文
    context_parts = []
    for doc, meta, dist in zip(results["documents"][0], 
                                results["metadatas"][0], 
                                results["distances"][0]):
        # 过滤低相关性结果（distance > 1.0 表示相似度低）
        if dist < 1.0:
            context_parts.append(f"[{meta['source']}]\n{doc}")
    
    return "\n\n".join(context_parts)
```

**评估结果**（来自 evals/report.md）：
- RAG 相关用例通过率：100%（qa-001/002/003）
- 平均检索耗时：< 1s（Chroma 本地查询）
- 幻觉率：0%（护栏用例 guard-001/002 全部拦截）

### 工程权衡分析

#### 为什么选纯向量检索而非混合检索？

| 维度 | 纯向量检索（当前） | 混合检索（BM25 + 向量） |
|------|-------------------|------------------------|
| 实现复杂度 | 低（单检索器） | 中（双检索器 + RRF 融合） |
| 推理成本 | 低（1 次 Embedding） | 中（1 次 Embedding + BM25 计算） |
| 语义理解 | 强（向量空间匹配） | 强（向量 + 关键词） |
| 关键词精确匹配 | 弱（专有名词易漏） | 强（BM25 擅长） |
| 适用场景 | 文档语义丰富、关键词少 | 文档含大量专有名词、编号 |

**本项目选择纯向量检索的理由**：
1. 知识库文档短小（平均 < 500 字），语义连贯，无需复杂切分
2. 查询以自然语言为主（"开放时间""预约规则"），少见专有名词
3. 业务简单，召回 top-2 已满足需求（评估通过率 100%）

**何时需要升级混合检索**：
- 知识库扩展到 100+ 文档
- 出现大量专有名词（如设备型号、实验室编号）
- 用户反馈"搜不到"问题增多

#### Chunk 策略详解

**当前策略**：全文档入库（不切分）

**适用条件**：
- 文档长度 < 1000 token
- 文档语义连贯，无明显分段
- 检索目标为"整篇文档"而非"文档片段"

**进阶策略**（当文档变长时）：

| 切分方式 | 适用场景 | 实现复杂度 | 示例 |
|---------|---------|-----------|------|
| 固定长度切分 | 通用文档 | 低 | 每 500 token 切一块，overlap 50 |
| 按标题切分 | 结构化文档（Markdown/HTML） | 中 | 按 `#` `##` 切分 |
| 按段落切分 | 长文本 | 中 | 按 `\n\n` 切分 |
| 语义切分 | 复杂强关联文档 | 高 | 用 LLM 识别语义边界 |

**本项目为何不切分**：
- 4 个知识文档平均 200-300 字，切分后碎片化，反而丢失上下文
- 用户查询以"整篇规则"为目标（如"开放时间"对应整篇开放时间文档）

#### Embedding 模型选型对比

| 模型 | 维度 | 中文效果 | 推理速度 | 部署成本 | 本项目选择 |
|------|------|---------|---------|---------|-----------|
| bge-small-zh-v1.5 | 512 | ⭐⭐⭐⭐ | 快（< 50ms） | 低（本地） | ✅ **采用** |
| text-embedding-3-small (OpenAI) | 1536 | ⭐⭐⭐ | 中（API 延迟） | 中（API 费用） | ❌ 依赖外部 API |
| m3e-base | 768 | ⭐⭐⭐⭐ | 中（~100ms） | 低（本地） | ❌ 效果略逊 bge |
| bge-large-zh | 1024 | ⭐⭐⭐⭐⭐ | 慢（~200ms） | 高（模型大） | ❌ 过度设计 |

**选择 bge-small-zh-v1.5 的理由**：
1. 中文效果优秀（MTEB 中文榜单前列）
2. 推理速度快（本地 CPU < 50ms）
3. 模型体积小（~100MB），部署成本低
4. 维度适中（512），向量库存储压力小

#### Rerank 的必要性分析

**当前项目未使用 rerank 的原因**：
1. 知识库规模小（4 个文档），召回 top-2 已足够
2. 向量检索质量高（bge-small-zh 中文效果优）
3. 业务简单，无需二次打分

**何时需要引入 rerank**：
- 知识库扩展到 20+ 文档，召回 top-10 后需精筛
- 用户反馈"答案不准确"（召回了相关但非最优的文档）
- 需要提升答案质量（如从 top-5 中选出 top-2）

**Rerank 模型选型**：
| 模型 | 效果 | 推理成本 | 适用场景 |
|------|------|---------|---------|
| bge-reranker-base | ⭐⭐⭐⭐ | 中（~200ms） | 通用场景 |
| bge-reranker-large | ⭐⭐⭐⭐⭐ | 高（~500ms） | 对质量要求极高 |
| cross-encoder (MS MARCO) | ⭐⭐⭐⭐ | 中（~200ms） | 英文场景 |

### 成本分析

**当前方案成本**（单次问答）：
| 环节 | Token 消耗 | 计算成本 | 延迟 |
|------|-----------|---------|------|
| 知识库检索 | 0（向量计算） | ~50ms | < 1s |
| 大模型生成 | ~500 token（输入） + ~200 token（输出） | ~¥0.003 | ~2s |
| **总计** | ~700 token | **~¥0.003** | **< 3s** |

**升级混合检索 + Rerank 后的成本**：
| 环节 | Token 消耗 | 计算成本 | 延迟 |
|------|-----------|---------|------|
| 向量检索 | 0 | ~50ms | < 1s |
| BM25 检索 | 0 | ~100ms | < 1s |
| RRF 融合 | 0 | ~10ms | < 1s |
| Rerank（top-10 → top-2） | ~1000 token（输入） | ~200ms | ~1s |
| 大模型生成 | ~500 token（输入） + ~200 token（输出） | ~¥0.003 | ~2s |
| **总计** | ~1700 token | **~¥0.005** | **< 5s** |

**结论**：混合检索 + Rerank 成本增加约 60%，延迟增加约 60%。在知识库规模小、业务简单的场景下，当前方案已是最优性价比。

### 后续优化方向

**短期优化**（低成本，1-2 天）：
1. 增加相关性阈值过滤：`distance > 1.0` 的结果不注入上下文
2. 增加引用溯源：在回答中标注信息来源（如"根据《开放时间》文档..."）
3. 增加评估指标：用 Ragas 评估 faithfulness / answer_relevancy

**中期规划**（中等成本，1-2 周）：
1. 升级混合检索：BM25 + 向量检索，RRF 融合
2. 引入 Rerank：bge-reranker-base，对召回结果二次打分
3. 优化 Chunk 策略：按标题切分（适配文档增长）

**长期愿景**（高成本，1-2 月）：
1. 实现 GraphRAG：提取实体关系，构建知识图谱
2. 实现 Agentic-RAG：Agent 自主决策是否改写 Query、是否多轮检索
3. 对接外部知识库：API 文档、FAQ 库、历史工单库

## 面试话术总结

### Q1: "你们的 RAG 是怎么做的？"

> "我们用的是标准 RAG 方案：离线构建知识库（bge-small-zh-v1.5 向量化 + Chroma 存储），在线查询时向量检索 top-2 相关文档注入上下文。知识库规模较小（8 个实验室 + 4 个规则文档），所以选择了纯向量检索而非混合检索，评估通过率 100%，成本约 ¥0.003/次。"

### Q2: "为什么不用混合检索 + Rerank？"

> "混合检索适合文档含大量专有名词、编号的场景（如设备型号、实验室编号），我们当前知识库以自然语言为主，纯向量检索已满足需求。Rerank 适合知识库扩展到 20+ 文档、需要精筛 top-5 的场景，我们当前 top-2 已足够。后续如果知识库扩展或用户反馈'搜不到'，会考虑升级。"

### Q3: "如何评估 RAG 的效果？"

> "我们从三个维度评估：① 召回率：用 evals 脚本的 qa 用例验证（当前 100%）；② 幻觉率：用 guard 用例验证（当前 0%，护栏全部拦截）；③ 成本：单次问答约 ¥0.003，延迟 < 3s。后续计划引入 Ragas 框架，自动评估 faithfulness / answer_relevancy。"

### Q4: "如果让你优化 RAG，你会怎么做？"

> "短期：增加相关性阈值过滤（distance > 1.0 不注入）和引用溯源（标注信息来源）。
> 中期：升级混合检索（BM25 + 向量 + RRF）+ 引入 Rerank（bge-reranker-base），适配知识库扩展。
> 长期：实现 GraphRAG（提取实体关系）+ Agentic-RAG（Agent 自主决策检索策略），应对复杂业务场景。"
